# Задание 2. Мониторинг

## 1. Мотивация
На данный момент система частично мониторится через Яндекс Метрику, но после появления оформления заказов через API этих данных стало недостаточно. Метрика хорошо показывает поведение пользователей сайта, но не даёт понимания, что происходит внутри системы: как работают API, где возникают задержки, теряются ли заказы, перегружается ли база данных или очередь сообщений.
С учётом текущих проблем (долгая загрузка MES, рост количества заказов и API-интеграций, риск потери заказов) мониторинг необходим, чтобы: 
понимать реальную нагрузку на сервисы и БД; 
* быстрее находить причины медленной работы MES; 
* обнаруживать ошибки и зависшие заказы; 
* иметь данные для принятия решений об оптимизации и масштабировании.
Для бизнеса это важно, поскольку:
* позволит узнавать о сбоях до того, как клиенты начнут жаловаться;
* даст понимание, почему уходят партнеры (может, API тормозит?);
* даст фактуру для обсуждения с клиентами ("Вот лог, ваш заказ был отправлен").

Без мониторинга дальнейшее развитие системы и оптимизация будут происходить «вслепую».

### Сколько стоит отсутствие мониторинга?

**Прямые потери:**
- 3 крупных контракта с партнерами уже потеряно → ≈ 15 млн руб/мес
- Рост жалоб от клиентов → отток B2C-клиентов → еще -5 млн руб/мес
- Операторы тратят часы на ожидание загрузки → зарплата впустую

[стоимостные оценки приведены для наглядности, в задании данных нет]

**Косвенные потери:**
- Репутация на рынке B2B
- Демотивация команды (постоянные пожары)
- Страх что-то менять (непонятно, что сломается)

**Инвестиции в мониторинг:** 2-3 недели работы команды → окупаются за месяц предотвращенными потерями.

## 2. Выбор подхода к мониторингу

Для мониторинга системы предлагается использовать комбинацию следующих подходов:
* RED (Rate, Errors, Duration) — для API-сервисов (онлайн-магазин, CRM, MES).
* USE (Utilization, Saturation, Errors) — для инфраструктурных компонентов (базы данных, RabbitMQ, контейнеры).
* Google SRE (4 золотых сигнала) - для бизнес-метрик
  
Такое разделение позволяет:
* контролировать качество работы API с точки зрения клиентов и партнёров;
* отслеживать перегрузки и узкие места на уровне инфраструктуры;
* обеспечивать контроль бизнес-показателей

### 2.1. Для сервисов (API, приложения) — RED

**RED** = Rate, Errors, Duration — стандарт для микросервисов

| Метрика | Что измеряет | Почему для «Александрита» |
|---------|--------------|---------------------------|
| **Rate** (RPS) | Количество запросов в секунду | Понимаем нагрузку, видим аномальные всплески (DDOS или партнер запустил рекламу) |
| **Errors** (кол-во ошибок) | HTTP 4xx, 5xx | Видим, когда API ломается, партнеры не могут создать заказ |
| **Duration** (latency) | Время ответа | Если API тормозит → партнеры уходят к конкурентам |

**Где применяем:**
- Онлайн-магазин API
- CRM API
- MES API
- API для партнеров

### 2.2. Для инфраструктуры (БД, серверы) — USE

**USE** = Utilization, Saturation, Errors — для ресурсов

| Метрика | Что измеряет | Почему для «Александрита» |
|---------|--------------|---------------------------|
| **Utilization** (% использования) | CPU, RAM, диск, соединения | Понимаем, не пора ли расширяться |
| **Saturation** (очереди) | Количество задач в очереди, длинные запросы | Видим, когда система задыхается (очереди растут) |
| **Errors** | Ошибки ввода-вывода | Диски умирают, сеть падает |

**Где применяем:**
- Базы данных (CRM, MES, Shop)
- RabbitMQ
- EC2 инстансы

### 2.3. Для бизнес-метрик — Четыре золотых сигнала Google

Google SRE выделяет 4 сигнала:
1. **Latency** (время ответа) — сколько ждет клиент
2. **Traffic** (трафик) — сколько заказов, сколько пользователей
3. **Errors** (ошибки) — не только HTTP 500, но и бизнес-ошибки (заказ не создан)
4. **Saturation** (насыщенность) — насколько система близка к пределу

**Для «Александрита» добавляем бизнес-метрики:**
- Количество созданных заказов (растет ли бизнес?)
- Время от создания до отправки заказа (держат ли обещание 3 недели?)
- Процент зависших заказов (самая важная метрика для бизнеса!)

## 3. Метрики для отслеживания

### Легенда:
- 🔴 — критичные (алармы, реагировать немедленно)
- 🟡 — важные (дашборды, тренды)
- 🟢 — опциональные (для отладки)

### 3.1. Интеграция CRM-MES (RabbitMQ)

| ID | Метрика | Зачем | Ярлыки (labels) | Приоритет |
|----|---------|-------|------------------|-----------|
| 1 | **Number of dead-letter-exchange letters** | Количество упавших сообщений. Если > 0 — заказы теряются! Нужно срочно разбираться. | `queue`, `reason` (почему упало) | 🔴 |
| 2 | **Number of messages in flight** | Сообщения, которые обрабатываются. Если растет → MES не справляется. | `queue` | 🟡 |

### 3.2. Нагрузка на API (RPS)

| ID | Метрика | Зачем | Ярлыки | Приоритет |
|----|---------|-------|--------|-----------|
| 3 | **RPS for shop API** | Базовый трафик. Падение → сайт не работает. | `endpoint`, `method` | 🟡 |
| 4 | **RPS for CRM API** | Работа менеджеров. | `endpoint`, `user` (опционально) | 🟡 |
| 5 | **RPS for MES API** | Работа операторов. | `endpoint` | 🟡 |
| 6-8 | **RPS per user** | Кто слишком много грузит (подозрительно). | `user_id` | 🟢 |

### 3.3. Ресурсы (CPU, RAM)

| ID | Метрика | Зачем | Ярлыки | Приоритет |
|----|---------|-------|--------|-----------|
| 9-11 | **CPU %** | Утилизация процессора. >80% → пора масштабировать. | `service`, `instance` | 🟡 |
| 12-14 | **Memory Utilisation** | Утечки памяти? Не хватает RAM? | `service`, `instance` | 🟡 |
| 15-16 | **Memory Utilisation for DB** | База данных — узкое место. | `db_instance` | 🔴 |
| 17-18 | **Number of connections to DB** | Слишком много соединений → база задыхается. | `db_instance` | 🔴 |

### 3.4. Базы данных (размер)

| ID | Метрика | Зачем | Ярлыки | Приоритет |
|----|---------|-------|--------|-----------|
| 23-24 | **Size of DB** | Растет ли БД? Не пора ли чистить/партиционировать? | `db_instance` | 🟡 |

### 3.5. Время ответа (Latency) — самое важное для клиентов!

| ID | Метрика | Зачем | Ярлыки | Приоритет |
|----|---------|-------|--------|-----------|
| 19 | **Response time for shop API** | Клиенты уйдут, если сайт тормозит. | `endpoint`, `percentile` (p50, p95, p99) | 🔴 |
| 20 | **Response time for CRM API** | Менеджеры не могут работать. | `endpoint`, `percentile` | 🟡 |
| 21 | **Response time for MES API** | Операторы злятся. | `endpoint`, `percentile` | 🔴 |

### 3.6. Ошибки HTTP

| ID | Метрика | Зачем | Ярлыки | Приоритет |
|----|---------|-------|--------|-----------|
| 25-27 | **HTTP 200** | Базовый успех. Смотрим тренд. | `service` | 🟢 |
| 28-30 | **HTTP 500** | СЕРВЕР ПАДАЕТ! Немедленный алерт. | `service`, `endpoint` | 🔴 |

### 3.7. Сессии и трафик

| ID | Метрика | Зачем | Ярлыки | Приоритет |
|----|---------|-------|--------|-----------|
| 32-34 | **Simultaneous sessions** | Сколько людей прямо сейчас? Планирование мощностей. | `service` | 🟡 |
| 35-40 | **KB transferred** | Сетевой трафик. Не платим ли лишнего облаку? | `service`, `direction` | 🟢 |

### 3.8. Дополнительные метрики 

| Метрика | Зачем | Ярлыки | Приоритет |
|---------|-------|--------|-----------|
| **Количество созданных заказов в час** | Бизнес-метрика. Растем или падаем? | `source` (B2C, B2B) | 🔴 |
| **Время от SUBMITTED до SHIPPED** | Сдерживаем ли обещание "3 недели"? | `order_type` | 🔴 |
| **Процент зависших заказов** | Заказы, где статус не менялся > N часов | - | 🔴 |
| **Глубина очереди RabbitMQ** | Не накапливаются ли сообщения? | `queue` | 🔴 |
| **Количество активных операторов** | Достаточно ли людей? | - | 🟡 |
| **SLA для B2B-партнеров** | Время ответа API для каждого партнера | `partner_id` | 🔴 |

## 4. План действий (драфт ТЗ)

Для внедрения мониторинга в системе планируются следующие шаги:

1 Развернуть систему мониторинга - Prometheus для сбора метрик и Grafana для визуализации.

2 Подключить сбор инфраструктурных метрик:
Настроить сбор CPU, memory и network-метрик для сервисов shop API, CRM API и MES API, а также для баз данных.

3 Подключить сбор метрик API-сервисов:
Добавить сбор метрик RPS, latency и HTTP-ошибок (4xx/5xx) для всех API.

4 Настроить мониторинг RabbitMQ:
Добавить метрики количества сообщений в очередях, сообщений в обработке и сообщений в dead-letter очередях.

5 Создать базовые дашборды:
Подготовить дашборды состояния API, MES и очередей сообщений для оперативного контроля.

6 Настроить алерты и маршрутизацию уведомлений:
* Настроить алерты на критические метрики (ошибки, задержки, saturation ресурсов).
* Технические алерты направлять команде поддержки, по необходимости DevOps-инженеру и тимлиду на рабочую почту.
* Бизнес-критичные алерты (риск потери заказов) дополнительно направлять продакт-менеджеру.

## 5. Показатели насыщенности (Saturation) и действия

### Что такое насыщенность?

Насыщенность — это степень "загруженности" ресурса. Когда ресурс насыщен, система начинает тормозить, растут очереди, падает производительность.

### 5.1. Для RabbitMQ

| Метрика | Порог | Действие |
|---------|-------|----------|
| Глубина очереди > 100 сообщений | 🟡 Желтый | Проверить, справляется ли MES. Скорее всего, MES тормозит. |
| Глубина очереди > 500 сообщений | 🔴 Красный | Срочно будить команду! MES не справляется, заказы копятся. |

**Автоматизация:**
- При желтом → тикет в Jira, уведомление в Slack
- При красном → звонок дежурному (PagerDuty)

### 5.2. Для баз данных

| Метрика | Порог | Действие |
|---------|-------|----------|
| CPU БД > 80% (5 минут) | 🟡 Желтый | Анализировать запросы, добавлять индексы |
| CPU БД > 90% (5 минут) | 🔴 Красный | Срочно! Либо убиваем тяжелые запросы, либо апгрейдим инстанс |
| Соединений > 80% от max_connections | 🟡 Желтый | Ищем утечки соединений в коде |
| Соединений = max_connections | 🔴 Красный | База недоступна для новых подключений! Авария! |
| Размер БД > 80% от диска | 🟡 Желтый | Планировать чистку или расширение |
| Размер БД > 95% от диска | 🔴 Красный | БД упадет через часы! |

### 5.3. Для API (латентность)

| Метрика | Порог | Действие |
|---------|-------|----------|
| p95 latency > 1 сек (MES API) | 🟡 Желтый | Операторы недовольны, ищем причины |
| p95 latency > 3 сек (MES API) | 🔴 Красный | Операторы не могут работать! Срочно оптимизировать |
| p95 latency > 500 мс (Shop API) | 🟡 Желтый | Клиенты начинают уходить |
| p95 latency > 2 сек (Shop API) | 🔴 Красный | Массовый отток клиентов! |

### 5.4. Для ошибок

| Метрика | Порог | Действие |
|---------|-------|----------|
| HTTP 5xx rate > 1% (5 минут) | 🟡 Желтый | Есть проблемы, разбираться в рабочее время |
| HTTP 5xx rate > 5% (5 минут) | 🔴 Красный | Срочно! Часть клиентов не может сделать заказ |
| Dead Letter Queue > 0 | 🔴 Красный | НЕМЕДЛЕННО! Теряются заказы! |

### 5.5. Бизнес-метрики

| Метрика | Порог | Действие |
|---------|-------|----------|
| Новых заказов = 0 за час | 🔴 Красный | Система не принимает заказы! Авария! |
| Время выполнения заказа > 4 недель | 🟡 Желтый | Нарушаем обещания клиентам |
| Время выполнения заказа > 6 недель | 🔴 Красный | Кризис! Заказы теряются в производстве |
